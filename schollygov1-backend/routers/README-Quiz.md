# Quizzes & Analytics (Core Engine) Module

This module powers the core learning and assessment loop of SchollyGo. It contains the logic for generating dynamic questions, tracking student progress, and calculating dynamic XP rewards based on user streaks and question difficulties.

## 1. Quiz Flows

### Flow A: Warm-Up Quizzes (Topic Level)
- **Scope**: Granular. Quizzes are generated for a specific Topic inside a Chapter.
- **Goal**: Calibration and Sandboxing.
- **Mechanism**: 
  - The API fetches questions from `quiz_questions` where `topic_id = {topic}` and `difficulty = {chosen_difficulty}`. 
  - Sorts by `seen_count ASC, is_correct ASC` to prioritize unseen or previously failed questions.
- **Rewards**: No XP is awarded (`earned_xp = 0`). It is considered a sandbox/practice environment.
- **Progress Impact**: Updates `user_topic_progress` mastery. Cannot exceed 40% mastery from easy warm-ups alone.

### Flow B: Adaptive Quizzes (Chapter Level)
- **Scope**: Broad. Quizzes pull questions from *all* active topics within a Chapter.
- **Goal**: Mastery testing and spaced repetition.
- **Mechanism**: 
  - The API uses an adaptive slot allocation algorithm. It allocates slots for "Coverage" (starved topics), "Spaced Repetition" (oldest topics), and "Weakness Targeting" (topics where the student has the lowest accuracy).
- **Rewards**: Awards Dynamic XP based on score, difficulty chosen, time taken, current daily streak, and weighted base XP.
- **Progress Impact**: Updates `user_chapter_progress`, `user_topic_progress`, `user_subject_progress`, updates Streaks, and records in `xp_logs`.

## 2. API Endpoints
- **`GET /quiz/topics/{topic_id}/questions`**: Fetches Warm-up quiz payload.
- **`GET /quiz/chapters/{chapter_id}/questions/adaptive`**: Fetches Adaptive quiz payload based on student's historic weakness data.
- **`GET /quiz/chapters/{chapter_id}/mistakes`**: Fetches up to 10 questions the user specifically got wrong in the past.
- **`POST /quiz/attempts`**: Core submission endpoint. Records the attempt, updates masteries, streak, and XP.

## 3. Database Transaction & Idempotency (`POST /quiz/attempts`)

Because this endpoint manages XP, Streaks, and Levels, it uses strict MySQL transaction blocks to guarantee atomicity.

1. **Transaction Begin**: `conn.begin()`
2. **Row Locking**: `SELECT ... FROM users WHERE id = %s FOR UPDATE` locks the user's row to prevent concurrent requests from calculating the wrong total XP (e.g., if a user submits two quizzes on two devices simultaneously).
3. **Idempotency Protection**: The payload requires an `idempotency_key` (UUID) generated by the frontend. The `quiz_attempts` table enforces a `UNIQUE` constraint on this column. If a double-click race condition occurs, MySQL raises a duplicate key error on the second attempt, which triggers a `ROLLBACK` to protect data integrity.
4. **Calculations**: Runs mastery calculations and dynamically assigns XP.
5. **Database Updates**: Inserts into `quiz_attempts`, `user_question_history`, `question_attempt_logs`, updates `user_mistake_lifecycle`, `user_topic_progress`, `user_chapter_progress`, `xp_logs`, and `users`.
6. **Transaction Commit**: `conn.commit()` is called. If any Python exception or MySQL constraint failure occurs, the `except` block catches it and issues a `conn.rollback()`.

## 4. Identified Gaps & Future Enhancements

During the module review, several areas for improvement were identified for future scalability and robustness:

### 1. Database Scalability Bottleneck (`FOR UPDATE`)
- **The Gap**: Currently, the `POST /quiz/attempts` endpoint uses `SELECT ... FOR UPDATE` row locking on the `users` table to guarantee atomicity for XP and streak calculations. At high scale, having hundreds of students submit quizzes concurrently could lead to lock contention and database timeouts.
- **The Enhancement**: Implement **Eventual Consistency** using a Message Queue (like RabbitMQ, Redis Streams, or Celery). Quiz submissions should immediately write the log to the database and return `200 OK`, while a background worker safely calculates and updates the `users` XP table asynchronously to avoid locks.

### 2. Basic Analytics Tracking
- **The Gap**: The system currently tracks whether a question was correct or incorrect, but lacks granular metadata required for advanced analytics.
- **The Enhancement**: Track **Time per Question** (e.g., student took 45s on Q1, 2s on Q2). This metadata is crucial for identifying "guessing" behaviors vs "struggling" behaviors.

### 3. Anti-Cheat Mechanics
- **The Gap**: A malicious user could sniff the API, capture the generated quiz payload, and instantly submit a 100% score payload bypassing the frontend constraints.
- **The Enhancement**: Implement Server-Side Quiz Sessions. When `GET /quiz/...` is called, the server should create a Redis cache record of the `session_id` and the `start_time`. The `POST /quiz/attempts` must require this `session_id`. The server can then reject submissions that are mathematically impossible (e.g., scoring 100% on a 15-question quiz in 3 seconds).

### 4. Item Response Theory (IRT)
- **The Gap**: Mastery percentages currently use a linear math model based on the raw count of correct answers.
- **The Enhancement**: Implement an **Elo-style Rating System** for both questions and students. If a student answers a historically difficult question correctly, their mastery jumps significantly more than if they answered an easy question correctly. Furthermore, question difficulty should self-calibrate based on global student fail rates.
### 5. "XP Farming" & Botting Constraints
- **The Gap**: Adaptive Quizzes award XP factoring in time taken. A script submitting quizzes in 0.5 seconds could farm XP, or a user leaving a tab open for 3 hours could receive an oversized time bonus.
- **The Enhancement**: Implement mathematical boundaries:
  - **Minimum Time Threshold**: (e.g., `< 2 seconds` per question yields 0 XP) to deter bots.
  - **Maximum Time Cap**: (e.g., time bonus maxes out at `120 seconds` per question) to prevent AFK farming.

### 6. The Question Exhaustion Gap
- **The Gap**: Highly active students might eventually answer every available question in a Chapter. The `GET /quiz/chapters/.../adaptive` endpoint might return an empty array or crash.
- **The Enhancement**: Implement a **"Review Mode" fallback**. If the user has exhausted all unseen/failed questions, the API should fetch previously answered correct questions but flag the payload as `is_review: true`. This flag should heavily throttle or cap the XP reward so users cannot endlessly farm easy questions for coins.

### 7. Graceful Idempotency Handling
- **The Gap**: While a MySQL duplicate key error triggers a `ROLLBACK` for double-clicks, allowing FastAPI to treat it as an unhandled exception results in a `500 Internal Server Error`, creating a poor UX (crash screen).
- **The Enhancement (Implemented)**: The backend now explicitly catches PyMySQL `IntegrityError (1062)` within the `POST /quiz/attempts` endpoint. It safely issues the rollback and translates the error into a clean `409 Conflict` (or can return a `200 OK` with the initial payload) so the frontend UI resolves gracefully without a crash screen.
